Three Next.js Route Handlers under `src/app/` form a small auth surface:
- `login/page.tsx` + `login/login-form.tsx` render the sign-in UI; `login/actions.ts` exposes `loginLearnerAction` (React 19 Server Action) backed by a reusable `loginLearner` core that validates via Zod (`@/lib/validation/auth`), calls `supabase.auth.signInWithPassword`, and returns a typed `LoginActionResult`. A parallel `logoutLearnerAction` performs `signOut`.
- `register/page.tsx` + `register/register-form.tsx` render the registration UI; `register/actions.ts` exposes `registerLearnerAction` backed by `registerLearner`, which validates via Zod, calls `supabase.auth.signUp` with `emailRedirectTo` pointing at `/auth/callback`, stores `full_name` as non-authoritative `user_metadata`, and is enumeration-resistant (duplicate-email errors return success).
- `auth/callback/route.ts` is a Next.js Route Handler (`GET`) that exchanges the one-time Supabase code via `exchangeCodeForSession`, sets cookies through `@supabase/ssr`'s server client, and redirects to a sanitized internal path.

Dependency direction is strictly inward: pages depend on their sibling `actions.ts`; actions import shared infrastructure from `@/lib/supabase/server` (Supabase anon client), `@/lib/supabase/env` (`getTrustedAppOrigin`, `SupabaseConfigurationError`), and `@/lib/supabase/redirect` (`sanitizeRedirectUrl`). No cross-imports exist between login and register modules. UI components come from the shared `@/components/ui/*` and `@/components/layout/container` primitives.
